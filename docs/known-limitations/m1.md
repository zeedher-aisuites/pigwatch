# M1 Known Limitations

M1 is a local-development telemetry backbone, not a production deployment or sensor product.

- The publisher has bounded in-memory retries but no durable outbox. Events can be lost before
  broker PUBACK or after retry exhaustion, so unconditional producer-to-database at-least-once
  delivery is not claimed.
- Broker persistence and the consumer session reduce ordinary restart loss but do not cover broker
  volume loss, session expiry, PostgreSQL loss or disaster recovery.
- Raw accepted/rejected MQTT evidence is retained without a production retention, deletion,
  encryption or authorization policy. Messages are bounded to 64 KiB.
- Anonymous MQTT and local database defaults are loopback-only development settings. Production
  MQTT authentication/TLS, API authorization and credential rotation are not designed.
- Only schema version `1.0` and three typed scalar fixture payloads are supported. There is no schema
  registry, automatic unit conversion or M2 acquisition/simulation behavior.
- Late events have a five-minute observable flag but no maximum age, watermark or stream window.
- The ingestion worker shares the API process. Independent scaling/deployment is deferred until
  measured operational evidence justifies another deployable.
- PostgreSQL has no partitioning, TimescaleDB extension, retention automation, backup or recovery
  plan.
- The initial migration downgrade drops M1 tables and is destructive; it is suitable only for
  isolated local/test rollback.
- The existing non-blocking GitHub Actions Node.js runtime deprecation warnings remain deferred
  maintenance and are unrelated to M1 telemetry behavior.
- Dashboard analytics, Digital Farm behavior, sensors, simulation ground truth, anomaly detection,
  alerts, LLMs and hardware adapters remain outside M1.
